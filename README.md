# Сервис поиска исполнителей

Учебный проект ПР3–ПР10. Заказчики размещают заказы, исполнители оставляют отклики;
сервис показывает платежи, отзывы и статистику. Веб-страницы используют Django ORM и
`db.sqlite3`. Консольная версия (`python main.py`) сохраняет работу с JSON.

## Запуск

Python 3.11+, Django 5.2. В PowerShell из корня проекта:

```powershell
.\dvenv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py import_legacy
python manage.py runserver
```

Импорт запускается **один раз**, только в пустые таблицы предметной области.
Источник — `data/freelance.sqlite` из ПР7; он открывается только для чтения.
Повторный импорт остановится без изменения данных. Для другого источника:
`python manage.py import_legacy --source путь/к/базе.sqlite`.
Сначала сделайте резервную копию существующей `db.sqlite3`.
Локальная база в Git не включается. Миграции сохранены в приложениях.

## Модели и перенос данных

`profiles.User`, `orders.Order`, `applications.Application`, `transactions.Transaction`,
`reviews.Review` связаны внешними ключами с `related_name` и `on_delete=PROTECT`.
Учётная запись администратора Django и участник сервиса — разные модели.
Нельзя удалить объект, на который ссылаются другие записи.
Сохраняются исходные ID; отсутствующие связи имеют `NULL`, исходный идентификатор
находится в `source_*_id` и отображается без ссылки. При переносе сохранены
4 участника, 2 заказа, 5 откликов, 10 платежей, 1 отзыв.
Пароли участников переносятся как хеши и не выводятся на страницы.
Старые контакты допускают произвольный текст, бюджет — строку или диапазон;
сумма платежа — Decimal, оценка отзыва ограничена диапазоном 1–5.
Старые `db/`, `sql/`, JSON и объектная консольная модель оставлены для ПР3–ПР7;
веб-представления их не вызывают.

## Страницы и запросы ПР9

| Раздел | Адрес |
| --- | --- |
| Главная | `/` |
| Заказы и карточка | `/orders/`, `/orders/<id>/` |
| Доступные новые заказы | `/orders/search/?q=...` |
| Статистика | `/orders/statistics/` |
| Отклики, платежи, отзывы, участники | `/applications/`, `/transactions/`, `/reviews/`, `/profiles/` |

Для каждого раздела есть карточка `/<раздел>/<id>/` и обработка 404.
Заказы фильтруются одновременно по имени/фамилии заказчика или названию (`Q`), статусу
и заказчику. Сортировка выбирается из разрешённого списка. При неверном фильтре
выводятся ошибки формы и пустой результат. `Paginator` выводит по 5 записей,
`{% querystring %}` сохраняет остальные GET-параметры. Неверный номер страницы
обрабатывается `get_page()`.

Реализовано более 15 отдельных выражений ORM в рабочих сценариях:
пять списков (`all`, `select_related`), пять карточек (`get_object_or_404`),
составной поиск `Q`, фильтры по статусу и заказчику, поиск новых заказов с `exclude`,
сортировки по названию и полям заказчика, `prefetch_related` откликов карточки,
`aggregate(Count)` общего количества и доступных заказов, группировка статусов,
`annotate(Count)` откликов, `Sum` оплаченных платежей, `annotate(F)` и `values`
для группировки по заказчикам, постраничная выборка. Создание, изменение и удаление
проверены тестами моделей. Статистика платежей и откликов вычисляется раздельно,
чтобы несколько JOIN не умножали результаты. Отменённые платежи не учитываются.
Аналог доступности помещений из методички — доступность новых заказов;
бронирование по датам не соответствует предметной области этого проекта.

## Проверка

```powershell
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py showmigrations
python -m pytest -v
python -m flake8 . --extend-exclude=dvenv
```

Тесты используют отдельную временную БД Django. Проверяются CRUD, защита связей,
валидация, фильтры, пагинация, 404, экранирование HTML, статистика и перенос данных.
Темы Яндекс Практикума применены в проекте; прохождение упражнений в личном кабинете
подтверждается отдельно студентом.

## Административная панель ПР10

Создайте учётную запись командой `python manage.py createsuperuser`, затем откройте
`/admin/`. Зарегистрированы все 5 моделей предметной области. Настроены русские
названия, `list_display`, `search_fields`, `list_filter`, `ordering`, `list_per_page=10`,
`list_select_related`, автодополнение внешних ключей. Карточка заказа содержит inline
откликов, платежей и отзывов, карточка участника — его заказы. Хеши паролей скрыты.
Доступ к админке требует входа сотрудника Django; публичные страницы доступны без входа.

`Order.Status` задаёт TextChoices NEW, IN_PROGRESS, PAID, COMPLETED, CANCELLED.
Менеджер OrderQuerySet предоставляет `available()`, `active()`, `search()` и
`with_customer()` и используется представлениями. Доступны только новые заказы;
активны новые и находящиеся в работе; отменённые, оплаченные и завершённые исключены.
Даты бронирований, вместимость и GeneratedField не вводятся: их нет в предметной области.
Карточки сохраняют адреса по ID, `get_absolute_url()` согласован с именованным маршрутом.
ПР10 не меняет схему БД; новые миграции не требуются (`makemigrations --check`).
Контекстный процессор передаёт название сервиса и число доступных заказов в общий footer.

## Анализ SQL

Установлен Django Debug Toolbar 6.3. Для локальных запросов при DEBUG=True справа
появляется вкладка SQL. В тестах и при DEBUG=False панель отключается.
В PowerShell её можно отключить: `$env:DJANGO_DEBUG_TOOLBAR='0'`.
Использована [официальная инструкция установки](https://django-debug-toolbar.readthedocs.io/en/stable/installation.html).
Список заказов использует COUNT для пагинации, JOIN заказчика и LIMIT страницы;
дополнительно запрашиваются варианты фильтра и число доступных заказов для footer.
Карточка заказа использует JOIN заказчика и два запроса prefetch для откликов и исполнителей.
Тест подтверждает 3 запроса получения связанных данных при 8 откликах: N+1 отсутствует.
Для просмотра SQL откройте `/orders/`, задайте фильтр и сортировку, затем SQL на панели;
сравните с `/orders/1/`. Агрегация платежей считает только paid, включая заказы без платежей.
В админке проверьте поиск заказов по имени связанного заказчика и фильтр по статусу.
